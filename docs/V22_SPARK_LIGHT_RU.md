# Spark light: установка, наблюдение и управление

Отдельный `monik-spark-agent` собирается для Linux ARM64 и работает одним
непривилегированным процессом. Резидентный `monik-service-host`, Docker-группа,
терминал агента и право запуска произвольных команд ему не нужны. Используется тот же контроллер Monik; машина использует прежний ID в общем списке и во вкладке
«Спарки». Наличие исходников, сборка, установка и итоговая приёмка — отдельные
этапы. Фактические результаты развёртывания фиксируются в отчёте исполнителя.

## Установка без изменения моделей

В «Добавить машину» владелец выбирает **Spark light / Linux ARM64** и свой
действующий HTTPS-адрес контроллера. Подготовленный однофайловый установщик
содержит индивидуальный профиль регистрации и поэтому должен храниться как
секрет. Повторная авторизация владельца для его скачивания сохраняется.
Общий шаблон установщика не содержит учётных данных.

Установщик проверяет фактическую архитектуру, flavor пакета, доверие к CA и
поддержку нужных возможностей контроллера. Затем применяется существующее
подтверждение регистрации. Начальная установка даёт наблюдение без управления
моделями; модельные unit/container, TUI, веса и скрипты не изменяются.

Для Linux служебная установка использует обычные защищённые бинарные и
state-пути, указанные в индивидуальном профиле. Команда `service plan` показывает
план, `service status` выполняет ограниченный реальный запрос состояния.
Не копируйте пример поверх занятого unit или существующей регистрации.

```sh
monik-spark-agent service plan --config /ABSOLUTE/STATE/agent.json
monik-spark-agent service status --config /ABSOLUTE/STATE/agent.json
```

Команды ниже выполняет локальный администратор с проверенным подходящим
бинарным файлом и действующей конфигурацией. `install` — явная локальная
установка/замена; `convert` — переход существующего полного агента в light;
`rollback` — возврат из сохранённой защищённой recovery-точки. Повторная
регистрация при конвертации не требуется. Сначала остановите только прежний
процесс мониторинга через поддержанный установщик, не модель.

```sh
sudo monik-spark-agent service install --config /ABSOLUTE/STATE/agent.json
sudo monik-spark-agent service convert --config /ABSOLUTE/STATE/agent.json
sudo monik-spark-agent service rollback --config /ABSOLUTE/STATE/agent.json
```

Recovery хранит прежние исполняемые файлы и unit; identity, текущие credentials,
CA, endpoint, spool и applied configuration сохраняются. Повреждённая или
неподходящая точка не превращается в новую пустую установку. Удаление мониторинга
не удаляет владельческие данные и не останавливает модель. Эти примеры описывают
доступный интерфейс; они не являются доказательством выполненной native приёмки.

## Наблюдение

Во вкладке «Спарки» доступны обзор, модели, хранилище и диагностика. GPU/CPU,
температуры, частоты, мощность, память, диски, сеть и процессы имеют источник,
время и качество. Нет доступа к датчику — показано «неизвестно» или «не
поддерживается», а не ноль. CPU и GPU GB10 используют единую память; показатели
не складываются в две независимые ёмкости. Загрузка интерфейса памяти не
подменяет объём занятой RAM.

Настройки модели и эффективный runtime показываются только как сведения.
Readiness подтверждается безопасным API-наблюдением, а не одним PID. SGLang
не проверяется через `health_generate`; wildcard listen не выдаётся за адрес
клиента. Обрыв связи оставляет последнее наблюдение с явной отметкой устаревания.

Обычный viewer видит разрешённое наблюдение. Профили управления, приватные
настройки и модельные логи доступны владельцу по отдельным правилам. Возврат
классификации машины из «Спарк» не выдаёт полномочий управления.

## Общий координатор семи профилей

Пять существующих V4-профилей — Qwen3 Coder Next, Ling, Mistral Small,
Nemotron и MiniMax — и два прежних профиля Qwen3.8/GPT OSS подключаются к
**одному существующему Python Coordinator**. Monik использует его StateStore,
общую блокировку и резервирование памяти; второго владельца инференса нет.
Исходный manifest пяти V4-профилей сохраняется, два legacy-профиля добавляются
проверенными фиксированными адаптерами. Текущий код и состав установки описаны в
[`tools/spark-controller`](../tools/spark-controller/README.md).

Root broker загружает проверенные исходники через запечатанные файловые
дескрипторы и связывает разрешение с точными ревизиями, исходниками, unit и
экземпляром. Имена прежних скриптов и TUI сохраняются; их фиксированные
делегаты обращаются к тому же координатору. Параметры моделей, веса и клиентские
бюджеты генерации не меняются при обновлении мониторинга. Наличие семи адаптеров
не означает, что семь движков запускались или прошли runtime-приёмку.

Конфигурация шаблона systemd проверяется через фиксированный экземпляр для
чтения метаданных. Он не становится запуском, поколением или доказательством
готовности. Для реального запуска проверяются его собственный unit и полная
физическая идентичность: owner, immutable container ID, время создания и
процесс. Имя контейнера и неактивный шаблон эту проверку не заменяют.

Каталог остаётся запасным вариантом для иных неподдержанных профилей.
Защищённый `configured-catalog.json` показывает только конфигурацию и явное
«состояние запуска не наблюдается», без придуманного PID, поколения или
статуса «остановлена». Каталог не даёт управления и логов. Это ограничение
не описывает текущую интеграцию семи поддержанных профилей.
Настройки thinking/effort, chunked prefill и квантования имеют явный источник.

## Локальное разрешение управления

Обнаружение процессов формирует кандидатов без права запуска. Локальный
администратор рассматривает конкретный системный unit или полную frozen
Docker-декларацию, безопасный health endpoint, модельные зависимости, память,
исключения и разрешённые источники логов. Проверенный root-owned policy и
typed Unix broker разрешают только указанное; пользователь браузера не передаёт
shell, argv, путь к файлу или Docker URL. Collector не получает root или доступ
к Docker socket.

Для существующих моделей учитываются реальные независимые CLI/TUI-пути и
общая блокировка развёртывания. Занятый lock не удаляется. Изменение определения
unit, параметров контейнера, ревизии профиля или экземпляра прекращает старое
разрешение. Неподдержанный launcher требует безопасной отдельной адаптации;
нельзя ослаблять проверку ради зелёной кнопки.

```sh
sudo monik-spark-agent approve --draft /LOCAL/REVIEWED/draft.json \
  --output /etc/monik-spark/policy.json --enable
sudo monik-spark-agent verify-policy --policy /etc/monik-spark/policy.json
```

Управление использует текущие owner/recent-auth, session, control epoch,
revision, generation и исходный срок команды. Start/stop/restart не откладываются
до будущего появления машины в сети. Повтор того же запроса согласует старый
результат; потеря ответа не является основанием нового эффекта.

Stop не требует доступных весов или достаточной памяти для нового запуска.
Он доступен при STARTING и при точно наблюдаемом standalone start preflight.
Перезапуск состоит из подтверждённого stop и отдельно разрешённого start;
старое разрешение не запускает новый экземпляр автоматически. Неизвестный
результат остаётся неизвестным. Выход из браузера/мониторинга не означает stop
модели. Отключение управления прекращает control/log sessions и не убивает
модельные процессы.

## Модельные логи

Логи открываются владельцем только из локально разрешённого источника для
точного профиля/экземпляра. Tail/live, pause/resume и потерянные записи имеют
ограниченные буферы. Секреты и управляющие последовательности фильтруются
до сетевой отправки и хранения буфера. Обычная SQLite-история не превращается
в хранилище сырых модельных логов. Отзыв session/прав закрывает поток;
disconnect не создаёт новый поток автоматически.

Для семи профилей используются фиксированные engine/action-источники,
максимум четыре upstream-потока и 16 viewers на host. Буфер ограничен
256 KiB на профиль и 1 MiB на host. Защищённый локальный набор значений для
редактора не публикуется; его неизменность проверяется на фактическом reader и
перед каждой выдачей. Отсутствие разрешённого файла, смена pin или недоказанная
принадлежность остаются явной ошибкой, а не пустым успешным журналом.

## Обновление и проверка

Spark light — собственный artifact flavor, а не переименованный полный ARM64
worker. Общие remote update, rebind, rollback и restart агента для direct light
закрыты до отдельного подписанного безопасного rollout. Рабочая локальная
замена/rollback описаны выше; при каждом обновлении сохраняются identity и
доверие. Новые профили не наследуют чужой controller URL.

Контроллер с optional Spark extension продолжает принимать обычных агентов.
Изменение extension под тем же session/sequence конфликтует с immutable receipt;
backfill не делает старое ready-наблюдение текущим. Старый контроллер получает
совместимые базовые данные, если это подтверждено соответствующим тестом;
недоступные Spark-возможности отмечаются явно.

Отчёты могут передаваться с gzip только после подтверждённого capability в
аутентифицированном ACK той же принятой sequence. Сжатие сохраняет исходные
JSON-байты и правила immutable receipt; сжатое и распакованное тела имеют
отдельные ограничения. Старый контроллер продолжает обычный обмен без gzip.

Полная приёмка включает unit/race, реальный собранный desktop/mobile/TV UI,
ARM64 install/convert/rollback, harmless native systemd/Docker canaries,
сравнение датчиков, ресурсы с учётом всех вспомогательных процессов и сохранение
работающего инференса. Synthetic fixture не доказывает качество/скорость модели
или real engine start/stop. Цели <=32 MiB steady PSS, <64 MiB при ограниченных
логах, <0,5% одного CPU core и <2 KiB/s фоновой телеметрии — измеряемые цели,
а не гарантии по размеру бинарного файла. Фактические цифры, пробелы измерения и
PASS/FAIL/NOT_RUN публикуются в [реестре приёмки](../ACCEPTANCE_LEDGER.md).
Там отдельно указаны точный исходный коммит, установленная batch-сборка и
фактические native/browser/resource-результаты. Семь профилей наблюдаются,
Ling сохранён, три безопасные команды и логи проверены. Целевые ресурсы пока
превышены: около24% одного ядра и до84MiB sampled PSS; ранние F3 canary-проверки
не заменяют запуск всех реальных движков. Полные цифры и ограничения есть в
[машиночитаемом результате](audit/validation-v22-spark-2026-10-15.json).
CPU <0,5% — инженерная цель, её превышение фиксируется измерением и само по себе
не означает запрет всей поставки. Реальные model start/stop/restart,
генерация и cold start требуют отдельного согласованного обслуживания.
