# V12: перед переносом VM и первым удалённым агентом

Это инструкция для владельца и локального Грока. Пакет содержит исходники, не готовые подписанные релизные бинарники. Репозиторий и текущая установка аудитором не изменялись.

## Решение о внедрении

V12 значительно усиливает уже работающие сценарии, но не подменяет реальные проверки службы. Для первого Linux-сервера разрешение на пилот даётся после проверки ниже. Автоматическое распространение на весь парк, установка Windows без проверки и перенос только файла базы НЕ считаются принятыми.

Самое важное новое подтверждение: настоящий подписанный переход рабочего агента на другой digest и восстановление после падающего кандидата прошли на Linux без root. Первый вариант теста выявил цикл повторного обновления; исправление сохраняет ожидающее действие до первого опроса нового процесса. Это не испытание обновления самого service-host.

## 1. Интеграция у Грока

Исходная база: `c2229685f76551bcbdb0bb89e1fe1adc16e28878`.

1. Проверить архив (`python3 verify_package.py`) и запустить только предварительную проверку (`python3 preflight.py /путь/к/monik_v2`). Ничего не сбрасывать и не копировать исходники поверх грязной рабочей папки.
2. В чистом worktree применить один `monik-audit12-fixes.patch`. Если main изменился, сравнить изменения и интегрировать вручную. Это не повод делать reset --hard.
3. Сначала собрать веб-интерфейс, затем сервер. Запустить `scripts/verify-audit12.sh --with-browser` в Linux с Go из go.mod, Node 22, Python Playwright и разрешённым Chromium. Скрипт не устанавливает службы, не изменяет firewall и не обращается к боевому адресу. Для native-теста нужны только собранные локальные бинарники; временный контроллер и его ключи создаются отдельно.
4. Сохранить реальный результат. Любое падение должно останавливать внедрение до разбора. Отсутствие Chromium не означает, что UI принят. Проверка TypeScript не заменяет клики.
5. Коммитить интегрированный код только после проверки, затем собирать выпуск с правильным commit/version. Не выдавать локальные audit12-бинарники за подписанный релиз.

## 2. Перед переносом контроллера в VM

Сохранить работающий аварийный доступ к текущему хосту и VM. Не тестировать восстановление на единственной боевой копии.

Определить реальный каталог данных из фактического ExecStart/аргументов, а не по предположению. Веб-экспорт измерений не является резервной копией. DB-only backup тоже не содержит всю мониторную.

Остановить/дождаться операций обновления, ребинда и изменения доверия. Уже выданную команду нельзя считать отозванной только по кнопке отмены. На время переноса полностью остановить контроллер и удостовериться, что второй процесс не работает. Сделать защищённую согласованную копию всего каталога состояния, внешних конфигураций и unit/environment-файлов. Включить SQLite и оставшиеся WAL/SHM, original CA/TLS, secret-master.key, исходную идентичность, настройки, доверие и версии обновлений, каталог релизов, console-targets при использовании и другие реально указанные внешние файлы. Не загружать это в Git и не присылать в чат.

Проверить копию отдельно: количество машин, controller_id, имена, пины, настройки запросов, ключи доверия и возможность прочитать зашифрованные секреты. Только затем разрешать одному контроллеру работать с агентами. Вторую старую копию не запускать параллельно. Новый V12-lock защищает одну локальную папку, а не две VM с копиями базы.

V12 откажется стартовать при утраченной базе рядом с ключами, недостающей идентичности или несовместимой CA. Это защита. Не лечить её удалением ключей/журналов или начальной регистрацией. Восстановить исходный согласованный набор. Полностью автоматическая защищённая процедура disaster recovery ещё не реализована.

## 3. Первый Linux-агент

Собрать и передать согласованную пару `monik-agent` + `monik-service-host` из этого исходного дерева. Сохранить независимый SSH или консоль провайдера. Адрес из профиля должен быть реально доступен с удалённого сервера; не подменять его старым bootstrap IP из ТЗ.

Для НОВОЙ машины загрузить доверенный профиль из интерфейса владельца. Для auto-discovery открыть ограниченное окно регистрации, затем сверить отпечаток и одобрить машину. Профиль должен задавать подходящий системный `state_dir`, обычно `/var/lib/monik-agent`, а не случайную домашнюю папку root. Выполнять setup только для новой регистрации.

Пример команд при стандартном системном каталоге (пути к доставленным бинарникам и профилю проверить):

```sh
sudo ./monik-agent setup --profile /защищённый/путь/profile.json --non-interactive
sudo ./monik-agent service install --config /var/lib/monik-agent/agent.json
sudo systemctl is-active monik-agent.service
sudo systemctl show monik-agent.service -p User -p MainPID -p ExecStart
sudo journalctl -u monik-agent.service -n 80 --no-pager
```

Для УЖЕ зарегистрированной машины setup не запускать. Сохранить её защищённое состояние, остановить штатную службу и обновить пару средствами установщика, используя существующий путь конфигурации. Проверить, что active worker берётся из приватного state/bin, service-host защищён от записи обычными пользователями, служба работает от предусмотренной учётной записи monik, а не из неожиданной root-оболочки. Не запускать второй foreground-агент одновременно со службой.

На контроллере проверить один и тот же agent_id, правильный hostname/пользовательское имя, свежие CPU/RAM/диски, интервалы и применённую ревизию. Не путать успешную аутентификацию с измерениями и установкой службы. Отсутствующий температурный датчик не должен показывать 0 градусов.

Включить только нужные сервисы. Раздельно выбрать «Проверять» и «В обзоре». Проверить кастомный запрос на контролируемом приложении и убедиться, что выключенный сервис больше не получает периодические запросы. Автообнаружение неизвестного слушателя допускает ограниченное первичное определение.

Проверить `systemctl restart`, затем перезагрузку тестовой машины при сохранённом аварийном доступе. После старта не должно требоваться входить в desktop; agent_id/адрес/ключ/настройки не меняются. Это обязательная локальная проверка, в аудиторском контейнере она не выполнялась.

## 4. Обновление и отказ

Только на пилотной машине: подписать корректный тестовый выпуск доверенным ключом, импортировать и выбрать один агент. Дождаться новой сессии/digest и полного периода наблюдения, не только принятия команды. Провалившийся тестовый кандидат проверять лишь на отдельной VM с аварийным доступом.

Новый реальный тест использует отдельный работающий ELF с инертным добавлением байтов, затем подписанный немедленно завершающийся кандидат. Он доказывает механизм, но не совместимость произвольного будущего изменения формата состояния. Проверять конкретную пару версий отдельно.

При ошибке блок раскатки должен остаться заблокированным, прочтение уведомления ничего не разрешает. Не повторять вручную неизвестное обновление и не исправлять статус SQL-командой. Старый сервер не запускать при активных v11-заданиях с удержанием/партиями. Независимая замена самого service-host пока запрещена до реализации внешнего восстановления.

## 5. Что должно остановить раскатку

- Любой красный обязательный тест, ошибка загрузки UI или падение native signed-update сценария.
- Потеря/смена controller_id, agent_id, CA или ключа секретов при обычном обновлении.
- Новые сессии агента каждые несколько секунд во время одного обновления.
- Два процесса одной роли на одной папке либо неожиданные права на защищённые файлы.
- Утверждение «восстановлено» при неудачной записи recovery-журнала.
- Отсутствие резервного доступа перед перезагрузкой удалённого сервера.

## 6. Что остаётся неподтверждённым

Настоящие systemd/SCM boot/power loss, Windows ACL/service identity, независимый service-host rollback, полный restore, физический телевизор/Яндекс, мобильные устройства, большое количество машин и суточный прогон. Закрывать эти пункты только конкретным журналом испытаний на выбранной версии. Веб-консоль остаётся отдельным SSH-подключением; не делать её единственным аварийным доступом.
