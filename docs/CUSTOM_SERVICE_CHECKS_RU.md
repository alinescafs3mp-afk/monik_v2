# Monik: пользовательские запросы и рекомендации агента

Это руководство к исходному коду Audit 4 от `4f85de3`, не подтверждение обновления вашей установки. Для новых возможностей необходимо обновить сервер с интерфейсом и агент. Адрес существующего контроллера, регистрации и секреты не сбрасываются.

## Быстрый сценарий

Откройте Машины -> нужная машина -> Сервисы -> Кастомный запрос. Выберите найденный сервис. Укажите метод, адрес/путь, интервал, таймаут и ожидаемый ответ. Нажмите «Пробный запрос», посмотрите его результат, затем отдельно «Сохранить проверку». Пробный запрос не сохраняет определение и не запускается на центральном сервере: его выполняет агент этой машины.

Сохранено сервером, получено агентом, применено и подтверждено результатом являются разными этапами. Когда агент не на связи, операция остаётся ожидающей. Отказ, истечение срока и неизвестный результат не выдаются за успешный HTTP-ответ. Ссылка на операцию остаётся в Центре операций.

Уже сохранённая проверка не заменяется автоматическим обнаружением. Выбранную рекомендацию можно взять в черновик, проверить и сохранить. Пауза/игнорирование при редактировании сохраняются. Пробный запрос к такой проверке разрешён только отдельным нажатием и не включает периодический опрос.

## Пример: собственный JSON health endpoint

Допустим, ваше приложение документирует `GET /internal/ready?detail=brief` и отвечает `{"ready":true}`.

| Настройка | Значение |
|---|---|
| URL | `http://127.0.0.1:8080` |
| Путь и query | `/internal/ready?detail=brief` |
| Метод | GET |
| Интервал / таймаут | 15 / 3 секунды |
| Назначение | Готовность к работе |
| Тип проверки | Все заданные условия |
| HTTP-код | 200 |
| Поле JSON / тип / значение | `ready` / логическое / `true` |

Это иллюстрация, не утверждение о наличии такого сервиса на ваших машинах. Для массива можно указать `/checks/0/ok`, для вложенного поля `result.status`. Сравнение типов не превращает строку `"false"` в логическое `false` автоматически. Подстрока, JSON, код и задержка, когда они заданы вместе, должны пройти одновременно.

## Пример: документированный POST RPC

Только если приложение документирует дешёвый запрос без изменения состояния:

```json
{"jsonrpc":"2.0","id":1,"method":"health","params":[]}
```

Метод POST, открытый заголовок `Content-Type: application/json`, путь из документации вашего RPC-сервиса. Например, для ответа `{"result":{"status":"ok"}}` выберите HTTP 200 и `result.status` = строка `ok`. Подтвердите безопасность периодического POST. У встроенного примера интервал не меньше 30 секунд, но его можно изменить в допустимых пределах. **Метод health не является универсальным стандартом JSON-RPC.** Не отправляйте пример вслепую неизвестному приложению.

Возможны другие документированные JSON/текстовые/form запросы, но только в рамках HTTP(S). Monik не разбирает строку cURL и не запускает её в shell. DELETE, PUT, TRACE, CONNECT, произвольные двоичные диалоги и удалённые команды здесь не поддерживаются.

## Заголовки, секреты и виртуальные хосты

Открытые заголовки задаются JSON-объектом со строковыми значениями. Токен Authorization/Cookie/API-key должен быть отдельным секретом. Его значение обычно включает нужную схему, например `Bearer …`; Monik не угадывает способ авторизации.

Секрет создаётся в разделе «Агент и конфигурация» этой машины, затем выбирается в редакторе проверки. Нужна недавняя аутентификация. Для чувствительного тела создайте секрет с назначением `Body` и выберите его вместо открытого тела. Body здесь внутреннее назначение, не обязательный отправляемый заголовок. Открытое и секретное тело нельзя использовать одновременно. При выборе секрета тела открытый черновик тела очищается.

Прямые секреты в query и очевидные поля password/token в открытых шаблонах отклоняются. Это защита от распространённых ошибок, не универсальный анализ конфиденциальности: произвольный открытый текст может содержать секрет с неожиданным именем. Не помещайте такие данные в публичный шаблон.

Для виртуального хоста можно задать URL `https://app.internal:8443`, соединение `127.0.0.1:8443`, Host и TLS Server Name `app.internal`. Агент соединяется с указанным локальным IP, а не начинает сканирование удалённой сети. Сертификат должен доверенно подтверждаться. Настройка отдельной CA/mTLS для каждой проверки этим пакетом не добавлена; используйте корректное системное доверие или завершите соответствующую функцию, не отключайте TLS автоматически.

## Как понимать результаты

| Результат | Смысл и действие |
|---|---|
| refused | TCP отверг соединение до отправки HTTP. Проверить слушающий процесс, IP-семейство, порт, опубликованный порт контейнера. Другой JSON это не исправит. |
| TLS error | Соединение не подтвердило TLS. Проверить протокол, имя и доверие, а не ослаблять health-условия. |
| 401 / 403 | HTTP отвечает, доступ не разрешён. Нужен правильный секрет/разрешение. |
| 404 | Маршрут не найден. Проверить path, Host и приложение за портом. |
| 405 | Метод не принят. Использовать документированный метод. |
| 200 + неверное JSON-поле | HTTP ответил, но прикладная проверка не пройдена. |
| 503 readiness и 200 liveness | Процесс отвечает, но готовность не подтверждена. Нельзя скрывать первое вторым. |
| Нет новых данных | Нет свежего доказательства, не 0 и не автоматически «здоров». |

Результат содержит код, длительность, тип ответа и небольшие распознанные health-признаки, но не полный HTML/JSON ответ. Длительность относится к ограниченной попытке запроса; таймаут не является успешным HTTP RTT.

## Что именно делает автоматическое обнаружение

Агент перечисляет доступные локальные TCP-слушатели, различает IPv4/IPv6 и ограниченно проверяет HTTP/HTTPS. Дальше пробует конечный набор распространённых health-путей. Он не подбирает пароли, не читает весь сайт, не вызывает POST, не создаёт inference-задачи и не обходит TLS.

Рекомендация хранит время, причину, проверенный адрес и степень уверенности. Текущее состояние сервиса и старое наблюдение обнаружения не смешиваются. Повторный совет кешируется на десять минут; ручное повторное обнаружение сбрасывает кеш.

Автоприменение допустимо только для нового сервиса без существующей проверки: нужен ясный health-ответ и отрицательный контроль отсутствующего маршрута. Одинаковое «OK» на всех URL, HTML/страница входа, пустое 200 или неоднозначная ошибочная readiness-точка требуют ручного решения. Пустой документированный `/health` вполне можно настроить вручную на 200, просто одного пустого ответа недостаточно для автоматического доказательства здоровья.

Для уже обнаруженных сервисов после обновления запустите «Повторить обнаружение», откройте рекомендации, возьмите подходящую в черновик и выполните пробный запрос. Мониторная не должна сама заменить вашу настроенную проверку на более удобную зелёную.

## Ограничения этой реализации

Одна основная проверка на сервис. Отдельные параллельные readiness/liveness/функциональные проверки и нативные TCP/gRPC-пробы пока являются следующими задачами, не скрытыми настройками. Скрытые виртуальные хосты и контейнерные сети могут потребовать явного URL/dial/Host/SNI и разрешённого пути.

Интервал 5..3600 секунд с шагом 5, таймаут 1..30 секунд и меньше интервала. Тело 16 КиБ, ответ 64 КиБ. Одновременно до 16 периодических и двух пробных запросов. Это ограничения работы, не обещание точной частоты под любой нагрузкой.

Секреты после получения кешируются в памяти. Полноценное защищённое восстановление их кеша после перезапуска без сети пока не завершено. Самообновление служебного компонента, полный restore и прочие блокеры релиза остаются в `RELEASE_COMPLETION_PLAN.md`.
